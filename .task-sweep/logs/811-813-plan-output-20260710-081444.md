## Implementation plan

### Minimal shared contract

Two invariants, one per issue:

1. **Placement (#811):** Pooled note placement in `new` must use the same resolution as schema tooling: explicit `output_dir` option > owned-note placement via `ensureOwnedOutputDir` (existing bypass, unchanged) > `getOutputDir(schema, typeName)` (explicit type dir → ancestor explicit dir → `computeDefaultOutputDir` pluralized hierarchy). The "no outputDir → error" path disappears.
2. **Identity (#813):** `frontmatter.name` is always persisted and always equals the *pre-sanitization* identity string. Sanitization in `paths.ts` remains a filename-only concern and must never feed back into frontmatter (it already doesn't mutate — keep that property; the fix is to assign `name` upstream).

### Exact likely edits

- **`src/commands/new/write-plan.ts`** — delete the private `getTypeDefByPath(...)?.outputDir` helper and its error branch; call public `getOutputDir(schema, typeName)` from `src/lib/schema.ts`. Preserve the precedence order above verbatim.
- **`src/commands/new/interactive.ts`** — in all three branches (plain name prompt, fully-resolved filename pattern, unresolvable-pattern fallback prompt), assign `frontmatter.name = itemName` *before* the write plan / `paths.ts` runs.
- **`src/commands/new/json-mode.ts`** — explicit input `name` always wins (current behavior, keep). New: when `name` is absent and a filename pattern fully resolves, persist the resolved pattern string (unsanitized) as `frontmatter.name`. The "no pattern and no name → required error" path stays.
- **`src/commands/new/paths.ts`** — no changes; add a comment if useful, but it must stay non-mutating.

### Interactive identity semantics

- **Fully resolved pattern:** the pattern result *is* the identity (the user never typed a name), so persist the pattern output pre-sanitization as `name`; the file gets the sanitized form.
- **Prompted / fallback name:** persist exactly what the user typed; sanitize only for the path.
- **Templates:** if a template literal sets `name`, decide precedence explicitly (recommend: user/pattern identity overwrites template literal, since identity is per-instance) and test it either way.

### Tests preventing sanitized text from leaking into identity

- Interactive PTY simple flow: type a name requiring sanitization (e.g. `Foo/Bar` or `Foo: Bar`); assert file is `FooBar.md`-style *and* `frontmatter.name` equals the raw input. Extend the existing simple-flow assertions (currently type/status/priority only) to also assert plain-name persistence.
- Interactive with resolving pattern: assert `name` equals the raw pattern output, not the sanitized filename stem.
- Interactive fallback (pattern unresolvable): prompted name persisted verbatim.
- JSON: keep the existing `Foo/Bar` test; add pattern-resolves-without-name → `name` persisted from pattern; explicit name + pattern → explicit name persists while pattern drives the filename.
- A negative guard in each: when sanitization changed the string, assert `name !== <filename stem>`.

### Placement tests

- Computed hierarchy: deep type with no explicit dirs anywhere → pluralized `computeDefaultOutputDir` path; previously this errored — this is the core #811 regression test.
- Ancestor explicit dir with type-level dir absent → ancestor resolution used.
- Type-level explicit dir wins over ancestor/computed.
- Explicit `output_dir` option overrides all resolution.
- Owned note: pooled resolution bypassed even when the type has an explicit outputDir.
- Scaffolded child instances and forks: behavior-stability regression tests only (no code path changes intended).
- Errors: unknown type still fails cleanly; filename collision after sanitization (two identities collapsing to one filename) still triggers existing collision handling while both identities remain distinct in frontmatter.

### Ordering / reserved fields

`name` is a built-in; ensure assignment happens before the write plan's field-ordering/system-field pass so it serializes in canonical position (alongside `type`, before schema/template values, with system ID where the plan places it). Add/extend an ordering assertion in the field-ordering tests covering a note where `name` was pattern-derived. Verify validation treats `name` as built-in in all merged-frontmatter paths (JSON mode already accepts it).

### Docs

Remove the "temporary limitation" caveats in: `new` reference, schema reference, Quick Start, validation concepts, system-frontmatter product note (all under `docs-site/src/content/docs/`), README, and `docs/skill/SKILL.md`. Replace with the positive contract: pooled placement resolution order, and "`name` is always persisted and preserves identity even when the filename is sanitized or pattern-derived." Do not edit historical changelog entries.

### Compatibility risks

- Types lacking explicit `outputDir` no longer error at creation — notes silently land in computed dirs. Anyone relying on that error as a guard sees a behavior change; call it out in docs/PR description.
- Existing notes without `name` are untouched (no migration); only new creations gain the field — downstream consumers should tolerate both.
- Template-supplied `name` precedence is a new decision point; whichever rule you pick, pin it with a test.
- PTY assertions land in the separately-run PTY suite (a strict required check) — ensure they're in that suite, not the non-PTY gate. Run the full parity gate plus PTY locally; open as draft PR only.
