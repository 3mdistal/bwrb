**Non-blocking notes:**

1. **Interactive/JSON identity asymmetry with template-defaulted `name`.** JSON mode preserves an explicit `name` over pattern-derived identity (json-mode.ts:87 guard `=== undefined`), but the interactive pattern branch unconditionally overwrites `content.frontmatter.name` (interactive.ts:182–183), clobbering any template-defaulted `name`. Likely rare, but the two modes now diverge on the same input.

2. **Untested precedence claim.** Docs (docs-site/.../schema.md:111–114, new.md:207–210) promise "explicit type dir → explicit ancestor dir → computed hierarchy," but no new test exercises the *ancestor-directory* tier during creation. The computed test (new.test.ts:105–133) has no explicit dirs anywhere in the chain; the "explicit wins" test (new.test.ts:135–144) only covers the direct type. If `getOutputDir` regresses on ancestor precedence, nothing here catches it.

3. **Lost JSON-safe error path.** The removed mode-aware `throwJsonError` branch (write-plan.ts, deleted lines) means any failure inside `getOutputDir` in JSON mode would now surface as a plain thrown Error rather than structured JSON. Low risk since the type is validated earlier, but worth confirming `getOutputDir` is total for known types.

4. **No fork/owned coverage for the new resolution path.** The owned branch is unchanged and forks presumably reuse write-plan, but no test asserts fork or owned placement is unaffected by the `typePath` → `typeDef.name` switch — the one refactor with canonical-name risk. The slash-notation test (new.test.ts:146–162) mitigates this for pooled creation only, and only for a type with an explicit `output_dir`; slash-notation + computed fallback is untested.

5. **Style/consistency.** interactive.ts:183 mutates `content.frontmatter` in place while the two sibling branches use spread (interactive.ts:204, 217) — works (same object returned), but inconsistent.

6. **Doc placement nit.** docs-site/.../new.md:133–135 inserts the identity paragraph between "JSON mode includes `nameTransformed` metadata:" and its JSON example, orphaning the colon from its code block.

7. **Field-order contract now pinned only by regex.** The PTY assertion (new.pty.test.ts:150) locks `name` to last position after schema fields — good that it's asserted, but no non-PTY test pins the interactive ordering, and PTY tests are conditionally skipped (`describePty`), so field-order regressions could slip through environments where PTY tests don't run.
