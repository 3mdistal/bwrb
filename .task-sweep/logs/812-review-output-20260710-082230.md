## Blockers

None. The body-boundary logic, context clamping (`Math.max(source.bodyStartIndex, matchIndex - contextLines)`), and file-relative line preservation in `restrictMatchesToMarkdownBody` are coherent, engine-agnostic (applied after either `runRipgrep` or `runNodeFallbackSearch`), and the malformed-frontmatter fallback (`return 0`) is a deliberate, documented safe default. Docs, help text, changelog, and skill guidance all describe the shipped behavior, and scope is tight to #812.

## Non-blocking suggestions

1. **Phantom trailing "context" line** (`src/lib/content-search.ts`, `restrictMatchesToMarkdownBody`): `content.split(/\r?\n/)` on a newline-terminated file yields a trailing `''` element. Rebuilt `contextAfter` can therefore include an empty pseudo-line beyond EOF — the new test even codifies it (`contextAfter: ['Second body line for context.', '']` in `tests/ts/lib/content-search.test.ts`). ripgrep would never emit this line. Consider dropping a trailing `''` produced by the final newline before slicing context, and updating the test expectation accordingly.

2. **Eager whole-vault read** (`src/lib/content-search.ts`, `searchContent`): `loadSearchableFileSources` reads *every* candidate file into memory via unbounded `Promise.all` before the search runs, even though body boundaries are only needed for files that actually matched. On large vaults this doubles I/O (ripgrep reads files again) and holds all file contents in memory even for zero-match queries. Loading sources lazily for only the matched files after the raw search would avoid the regression.

3. **Limit interaction untested against frontmatter matches**: the `limit` tests were changed to a body-only pattern (`'deployment'`), which sidesteps rather than exercises the interesting case — a pattern matching frontmatter in some files and bodies in others under a small `limit`. The diff suggests `limit` isn't passed to the search engines (options object only carries `contextLines`/`caseSensitive`/`regex`), so filtering should happen before truncation, but a test asserting that frontmatter-only hits don't consume the limit would lock this in.

4. **No end-to-end CRLF coverage**: `findMarkdownBodyStartIndex` is unit-tested with pre-split CRLF-ish lines, but there's no fixture file with actual `\r\n` content run through `searchContent` to confirm line-number/context parity between ripgrep output and the `\r?\n`-split source rebuild.

5. **Test hygiene** (`tests/ts/commands/search.test.ts`): the diff retains two identical `'should filter results with --where expression'` tests (both updated to `'body status'`). Pre-existing duplication, but since both blocks were touched, deduplicating here would have been cheap. Similarly, `list.test.ts`'s fallback test now mutates shared fixtures with a try/finally restore — fine, but a per-test temp file would be more robust against mid-test crashes in `beforeEach`-less suites.

None of these affect merge readiness given the verification evidence provided.
