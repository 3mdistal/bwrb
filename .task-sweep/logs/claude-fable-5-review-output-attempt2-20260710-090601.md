The confirmed stale-lock race fix is sound: the naive mtime/unconditional-unlink lock in `src/commands/new/fork.ts` (removed lines ~271–305) is replaced by `withOwnershipFileLock` built on the existing token/inode/heartbeat/recovery primitive in `src/lib/lineage-lock.ts`, and `tests/ts/lib/note-id-lock.test.ts` directly regresses the original failure mode (old holder releasing a successor's lock at the same pathname, plus heartbeat-vs-stale-reap). Lock ordering is consistent across flows (lineage → assignment → registry), so no deadlock cycle: adopt (`src/commands/lineage/adopt.ts` ~86–105), fork (`ensureSourceId`), and registry mutations in `src/lib/note-id.ts` all follow it.

Non-blocking notes:

1. **adopt/delete race coverage is probabilistic and near-vacuous** (`tests/ts/commands/lineage-adopt.test.ts`, "stays consistent when adoption races fork and non-force deletion"): both exit codes accept `[0,1]`, so the test passes for any outcome, and the dangling-edge audit check only fires if the single `Promise.all` shot actually overlaps. The planning doc itself flagged delete lock-set overlap as the "highest-risk gap." Recommend a deterministic test: hold a lineage lock on the parent path and assert `delete` blocks (or vice versa) to prove the lock sets actually intersect. The doc claim in `docs-site/.../lineage.md` ("Concurrent fork, non-force delete, and adoption operations therefore serialize on every path they share") is asserted, not demonstrated.
2. **Committed planning artifacts**: `.task-sweep/logs/*` (three new files) leak a local absolute path (`/Users/alicemoore/...`), a private brief filename, and internal model/sweep metadata. Should be dropped from the PR and gitignored.
3. **Timing-sensitive assertion**: `note-id-lock.test.ts` `expect(Date.now() - heartbeatMtime).toBeLessThan(45)` with `heartbeatMs: 5` / `staleMs: 45` may flake on loaded CI. Consider asserting only monotonic mtime advancement.
4. **Vault-wide fail-closed is stricter than the stated contract**: `assertGraphSafe` in `adopt.ts` blocks adoption on *any* lineage issue anywhere in the vault, not just issues "touching either family." Safe direction, but an unrelated broken note elsewhere makes adoption unusable; worth documenting or scoping to the connected components.
5. **Lock hold breadth**: adopt holds the shared `fork-source-id.lock` for its entire execute critical section (two full vault snapshots + writes), vs. fork holding it only during backfill. Heartbeats make this safe, but it serializes all fork/adopt executes vault-wide; could be narrowed to the ID-decision window later.
6. **Misleading error text for prospective non-cycle issues**: in `assertGraphSafe(prospective, true)`, a non-cycle issue introduced only by the prospective edge would report "existing provenance is unsafe." Cosmetic, since the pre-edge check catches genuinely pre-existing issues first.
7. **Concurrent-edit clobber window**: an ordinary `edit` (which takes no lineage locks) landing between adopt's in-lock `readFile` and `writeFileAtomic` is silently overwritten. This is the same pre-existing exposure fork's backfill has, so not new, but worth an issue.
