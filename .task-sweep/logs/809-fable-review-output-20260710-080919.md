BLOCKERS

## Blockers

1. **Untested validation path for invalid `date_format` string values.** The new `date_format` option has no `options` enum guard (src/commands/config.ts:80–85), so the *only* pre-write protection for it is the full `BwrbSchema` parse — the exact contract stated for this change. Yet the negative test (tests/ts/commands/config.test.ts:279–300, "should reject invalid date settings without writing") only rejects `--json '42'`, a JSON *type* mismatch likely caught by a generic string check before any schema parse. There is no test that an invalid pattern *string* (e.g. `--json '"foo"'` or `'"MM-YYYY"'`) is rejected without writing. Since interactive edit accepts free text (config.pty.test.ts:209–229 types raw `DD/MM/YYYY`), an unverified parse guard here risks silently persisting an invalid `date_format` into `schema.json`. Add a rejected-string test mirroring the `'"week"'` granularity case.

## Non-blocking

2. **Default duplication / drift risk.** `getConfigValue` hardcodes `'YYYY-MM-DD'` / `'day'` (src/commands/config.ts:380–383) while the same defaults live in `CONFIG_OPTIONS.default` (lines 81, 89). Deriving the fallback from option metadata would prevent divergence.

3. **Docs claim vs. schema behavior worth confirming.** docs-site/.../config.md says `date_format` is a "Pattern string using `YYYY`, `MM`, and `DD` tokens … including" four formats. If the schema is actually a closed enum of those four, this reads as accepting arbitrary token combinations (e.g. `YYYY/MM/DD`). Tighten wording or list the exact accepted set; ties into blocker 1 since no test pins this down.

4. **Weak intermediate PTY assertion.** In the `date_granularity` PTY test (config.pty.test.ts:112–130), `waitFor('month', 2000)` after `Keys.DOWN` can pass trivially because "month" is already rendered in the option list before the keypress. The final schema assertion covers correctness, but the intermediate wait gives false confidence.

5. **Brittle key sequence in `date_format` PTY test.** The `DOWN, DOWN, ENTER` navigation (config.pty.test.ts:213–215) encodes an implicit menu layout ("keep / clear / enter new value"); a comment or `waitFor` on the menu items before navigating would reduce flake risk if the menu changes.

6. **Positive note (no action):** the contract test (config.test.ts:394–405) correctly enforces disjointness and full classification of `ConfigSchema.shape` keys, satisfying the "no drift" requirement; the `calendars` rejection test (lines 302–310) pins the #790 boundary. Docs updates (roadmap, SKILL.md, schema.md) accurately reflect the new editable set.
