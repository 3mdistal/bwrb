# Implementation Plan: Expose date settings via `bwrb config` (#809)

## Root cause

`ConfigSchema` accepts `date_format`, `date_granularity`, and `calendars`, but `src/commands/config.ts` gates everything through a hand-maintained `CONFIG_OPTIONS` allowlist that was never updated when the date fields landed. Both `config list` and `config edit` therefore reject valid schema keys.

## Recommendation on `calendars`

**Do not expose `calendars` here.** Rationale:

- It's a nested, super-refined object; a flat key/value `config edit --json` surface would push users toward hand-authoring complex JSON blobs with era/month/hour invariants — exactly what #790's guided flow exists to prevent.
- The issue explicitly scopes calendar authoring to #790.
- Optionally expose `calendars` in **`config list` output as read-only** (e.g., show calendar names or "N calendars defined") only if it's cheap; otherwise omit entirely and let #790 own both read and write. My recommendation: omit entirely — cleanest scope, no partial contract to preserve later.

So the added surface is exactly two keys: `date_format` and `date_granularity`.

## Minimal file changes

1. **`src/commands/config.ts`**
   - Add `date_format` and `date_granularity` to `CONFIG_OPTIONS` (with descriptions for interactive selection).
   - Extend the `getConfigValue` switch: `date_format` → schema value or effective default `YYYY-MM-DD`; `date_granularity` → schema value or `day`.
   - Extend `validateConfigValue`:
     - `date_granularity`: must be one of `day | month | year` (mirror the schema enum; ideally derive from the Zod enum's `.options` so it can't drift).
     - `date_format`: must be a non-empty string. Since schema-level validation accepts any string, add a light command-level sanity check: require the pattern to contain at least one recognized token (`YYYY`, `MM`, or `DD`). Keep it permissive — don't reject exotic-but-plausible formats; do reject empty/whitespace. If you prefer zero new policy, accept any non-empty string and let docs guide users; either is defensible, but the token check gives better UX with negligible risk.
   - Ensure the edit path still assigns to raw schema and goes through `writeValidatedSchema` (`BwrbSchema.parse` + `resolveSchema`) so a bad value never writes — this already exists; verify granularity failures short-circuit before write via `validateConfigValue`.

2. **Tests** (existing config command test file + a new parity test, see below).

3. **Docs**: canonical config doc under `docs-site/src/content/docs/` and `docs/skill/SKILL.md`.

## Output contract preservation

- Text output: new keys appear in `config list` (all) in the same `key: value` style as existing entries; specific listing (`config list date_format`) follows existing format.
- JSON output: keys appear alongside existing ones with effective defaults filled in. No changes to shape — just two additional entries. Verify against existing snapshot/assertion style in tests and update expected output accordingly.

## Parity test (allowlist vs schema, without auto-exposing future keys)

Add a test that asserts an **explicit, intentional relationship**:

```ts
const SCHEMA_CONFIG_KEYS = Object.keys(ConfigSchema.shape); // or the exported zod object
const EXPOSED = CONFIG_OPTIONS.map(o => o.key);
const INTENTIONALLY_UNEXPOSED = ["calendars"]; // documented: #790

expect(new Set([...EXPOSED, ...INTENTIONALLY_UNEXPOSED]))
  .toEqual(new Set(SCHEMA_CONFIG_KEYS));
expect(EXPOSED.filter(k => INTENTIONALLY_UNEXPOSED.includes(k))).toEqual([]);
```

Effect: when someone adds a schema config key, this test **fails** until they make a deliberate choice — add it to `CONFIG_OPTIONS` (safe to expose) or add it to `INTENTIONALLY_UNEXPOSED` with a comment/issue link. Nothing is silently exposed, and nothing silently drifts. Requires exporting or importing the config Zod shape into the test — confirm `ConfigSchema` (or the parent `BwrbSchema` path to it) is importable; export it if not (minor, low-risk change).

## Tests

**Focused unit/command tests:**
- `config list` (all): includes `date_format: YYYY-MM-DD` and `date_granularity: day` when unset (effective defaults), and set values when present. Both text and `--json`.
- `config list date_format` / `date_granularity` specific.
- `config edit --json` success for both keys; re-read to confirm persistence.
- Invalid `date_granularity` (e.g., `"week"`): error, non-zero exit, **schema file unchanged** (mtime/content check, mirroring the existing no-write test).
- Invalid `date_format` (empty string; if token check adopted, a token-free string like `"hello"`): error, no write.
- `calendars` still rejected by `config list calendars` / `config edit` with the existing unknown-option error message.
- The parity test above.

**Real CLI scenarios (non-PTY):**
- End-to-end: `bwrb config edit` via JSON to set `date_granularity month`, then confirm a downstream behavior if cheap (e.g., `config list --json` reflects it) — don't overreach into date-expansion integration unless a test harness already exists for it.
- Run full gate: build, verify:pack, typecheck, lint, knip (watch for knip flagging any newly exported schema symbol used only by tests — reference it appropriately or use knip's test entry config), non-PTY tests, schema/docs checks.

## Docs edits

- **Canonical config doc** (`docs-site/.../config` page): move `date_format` and `date_granularity` from "schema-only" into the configurable options table; document defaults (`YYYY-MM-DD`, `day`), the granularity enum, and pattern tokens with the common formats (`YYYY-MM-DD`, `MM/DD/YYYY`, `DD/MM/YYYY`, `DD-MM-YYYY`). Remove or update the #809 link; note `calendars` remains schema-only pending #790.
- **`docs/skill/SKILL.md`**: same update in agent-facing terms — date settings now editable via `bwrb config edit`, calendars still schema-only (#790).
- Ensure docs checks in CI pass (any doc-schema sync tooling).

## Risks & conflict cautions

- **`date_format` validation policy**: too-strict token checking could reject legitimate custom formats. Keep it minimal (non-empty + contains a token) and document; schema itself stays permissive, so there's no behavior divergence for schemas edited by hand.
- **JSON output drift**: adding keys to `config list --json` is additive but could break consumers doing strict equality; the issue says preserve contracts — additive keys are the standard interpretation, but check for exact-match assertions in existing tests/docs examples.
- **Merge conflicts**: `CONFIG_OPTIONS` and `getConfigValue` are hot spots (mention-tuning config is explicitly out of scope but may land concurrently) — keep the diff surgical and don't reorder existing entries.
- **Parity test import**: exporting the config schema shape may trip knip or create a new public API surface; scope the export narrowly (e.g., export just the key list or the schema object from its existing module).
- **Scope discipline**: no guided calendar flow, no calendar read-only listing (per recommendation), no mention-tuning keys, no changes to date expansion logic itself.
