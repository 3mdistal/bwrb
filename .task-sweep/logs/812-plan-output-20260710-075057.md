# Implementation Plan — Issue #812: `--body` must exclude YAML frontmatter

## 1. Shared seam and boundary strategy

Fix this once inside `src/lib/content-search.ts::searchContent`, upstream of the engine split, so `resolveTargets`, `handleContentSearch`, `list --body [--matches]`, the hidden `search` command, and every other consumer inherit the fix with no call-site changes.

Add a small pure helper, e.g. `getFrontmatterEndLine(raw: string): number` (0 if no frontmatter), that returns the 1-indexed line number of the **closing** delimiter:

- Frontmatter exists only if line 1 is exactly `---` (tolerate BOM, CRLF).
- Closing delimiter is the next `---` (or `...`) line.
- **Unterminated frontmatter → return 0** (treat entire file as body), matching gray-matter's behavior in `parseNote`. Do **not** derive the boundary by diffing `raw` vs gray-matter's `body` string — gray-matter normalizes whitespace/newlines and would break original line numbers. A manual line scan against the raw file is the only safe way to keep the line contract; add a comment noting it must stay semantically aligned with `parseNote`.

Per file, compute `bodyStartLine = frontmatterEndLine + 1` and pass it into both engines.

## 2. Line numbers and context hygiene

- Keep reporting **original 1-indexed file line numbers** — never renumber against the stripped body.
- Filter, don't rewrite: drop any match with `line <= frontmatterEndLine`; drop any context line with `line <= frontmatterEndLine`. This automatically prevents before-context from leaking frontmatter for matches immediately after the closing `---`, while after-context is unaffected.
- The closing `---` line itself must be excluded (it's a boundary line, not body).

## 3. Engine parity

**Ripgrep path (`runRipgrep`):** keep scanning whole files (avoids stdin-per-file batching loss). Post-filter parsed JSON events by each file's boundary. Two traps:

- If `-m`/max-count is currently passed to rg, frontmatter hits consume the budget before filtering. Remove/raise the rg-level cap and enforce `limit` in shared TypeScript code *after* boundary filtering, so both engines apply limits identically.
- Boundary lookup requires reading each file's head; cache `path → frontmatterEndLine` for the run so files aren't re-parsed per match event.

**Node fallback (`runNodeFallbackSearch`):** it already reads full content; simply start the line loop at `bodyStartLine` (or skip earlier indices) while preserving original indices for reported line numbers and context windows.

Route both engines through one shared post-filter/limit function to guarantee identical semantics for literal/regex, case sensitivity, context, and limits.

## 4. Tests

Unit (`tests/ts/lib/content-search.test.ts` + new boundary helper tests), run against **both** engines (force fallback):

- Frontmatter-only false positive: term appears only in frontmatter (e.g. `status:`) → zero matches.
- Term in both frontmatter and body → only body match, with correct **original** file line number.
- Match on first body line with `-C N` → context contains no frontmatter lines and no `---` delimiter.
- Literal vs regex, case-sensitive vs insensitive, context sizes, limit counting (limit must not be consumed by filtered frontmatter hits).
- Edge fixtures: no frontmatter, empty frontmatter (`---\n---`), unterminated frontmatter (whole file searchable), `...` closing delimiter, CRLF, BOM, `---` appearing later in body (horizontal rule) — must not be treated as a boundary.

Command tests: rewrite existing tests that search `status` (frontmatter-only) to search body text; add coverage that `list --body`, `list --body --matches`, and hidden `search --body` all agree, and that path/type/where filters and dashboards/bulk/audit targeting still resolve.

## 5. Docs and help

- `docs-site/src/content/docs/`: replace all "frontmatter included today" disclosures and issue #812 caveats with the shipped contract: *`--body` searches Markdown body only; YAML frontmatter is excluded; line numbers refer to the original file*.
- `docs/skill/SKILL.md`: same contract update for automation guidance.
- CLI `--help` text for `list --body`, `--matches`, and the hidden `search` command.
- Run docs checks/build gate; grep the docs tree for "812" and "frontmatter" to catch stragglers.

## 6. Edge cases and release risks

- **Behavior change:** users/scripts matching frontmatter keys via `--body` will silently get zero results. Call this out in the changelog as an intentional fix, and point to structured/`where` filters as the supported way to query frontmatter.
- **Boundary drift vs gray-matter:** the manual scanner and `parseNote` could disagree on exotic input (custom delimiters, leading blank lines). Pin behavior with the edge-case tests above; keep the helper conservative (frontmatter only when line 1 is a delimiter).
- **Limit semantics:** moving limit enforcement out of rg changes internals — verify no test asserted rg args.
- **Perf:** boundary computation is a cheap head-read per matched file with caching; negligible.
- Explicitly out of scope: any new frontmatter-search flag, changing engine selection, or altering non-`--body` search behavior.

Suggested order: helper + tests → fallback → ripgrep post-filter + limit relocation → command test rewrites → docs/help → full CI parity including PTY and docs gates.
