# Implementation Plan: Issue #810 — Sync completion candidates with registered CLI

## Root cause

The completion tables in `src/lib/completion.ts` are hand-maintained string lists, disconnected from the actual Commander registrations in `src/index.ts`. Drift accumulated in four places:

1. **Root**: missing `init`.
2. **Schema**: missing `types`, `fields`, `discover`.
3. **Template**: advertises a nonexistent `show` subcommand (plus positional logic/tests for it).
4. **Recent options**: missing `--open`/`-o`, `--app`, `--save-as`, `--force`.

Existing tests only assert *inclusion of selected items*, so drift is never caught.

## Minimal file changes

**`src/lib/completion.ts`** (only file with behavioral changes):

- Root candidates: add `init`. Do **not** add hidden `open`/`search` — policy unchanged.
- Schema candidates: add `types`, `fields`, `discover`.
- Template candidates: remove `show`; remove any positional-completion branch keyed on `show`.
- Recent option candidates: add `--open`, `-o`, `--app`, `--save-as`, `--force` alongside existing selectors/limit/output flags.

**Positional cleanup for `template show` removal:**
- Delete the positional-argument completion path that offered type/name completion after `template show`.
- Confirm `template list <type> <name>` positional completion (the current detail surface) already handles type-then-name; if the removed `show` logic was the only place providing name completion at depth 2, port it to `template list` — but only if `template list` genuinely accepts that positional per built help. If it already exists, this is a pure deletion.
- Remove/update `show`-specific assertions in `tests/ts/lib/completion.test.ts`.

No changes to `src/index.ts` (registration is correct; completion is what drifted).

## Stable test strategy (anti-drift contract)

Add contract tests that compare completion tables to the **built CLI's help output**, since the suite already builds before command tests:

1. **Root contract**: parse visible command names from built root `--help`; assert set equality with root completion candidates. Because hidden commands don't appear in help, this naturally excludes `open`/`search` without hard-coding hidden-command knowledge into an exclusion list. Add one explicit guard: completion candidates do **not** contain `open` or `search` (locks the policy).
2. **Schema contract**: same set-equality against `schema --help` visible subcommands.
3. **Template contract**: same against `template --help`; implicitly proves `show` is gone.
4. **Recent options contract**: parse long flags (and `-o` short alias) from `recent --help` options section; assert the completion option list is a superset (or exact set, if the parser is reliable) of shipped flags. Prefer set equality if help parsing is clean; fall back to "help ⊆ completion" if formatting is fragile — equality is what actually prevents future drift in both directions.

Keep parsing simple and stable: match the indented command/option lines in Commander's help format; avoid regexes sensitive to description text. Run non-PTY (matches CI).

Also update the direct unit tests in `tests/ts/lib/completion.test.ts`: add inclusion assertions for `init`, `types`, `fields`, `discover`, and the four recent flags; remove `show` assertions.

## Risks and edge cases

- **Help-parsing brittleness in contract tests**: Commander formatting changes (wrapping, aliases like `-o, --open`) can break parsers. Mitigate with tolerant line parsing (split on first whitespace after trimming; handle `short, --long` option syntax explicitly).
- **Hidden-command coupling**: set-equality against help is correct only because hidden commands are absent from help. Add the explicit negative assertion for `open`/`search` so a future change to hidden rendering fails loudly rather than silently teaching them.
- **`template show` removal fallout**: other completion paths or shared positional helpers may reference `show`; grep the completion module and its tests fully. Knip will flag orphaned helpers.
- **`-o` short-flag handling**: verify the completion engine handles short flags at all; if the candidate table is long-flags-only by design, include `--open` and confirm `-o` behavior matches existing short-flag conventions rather than inventing new handling.
- **Command aliases**: if any subcommand has an alias, decide whether completion offers alias, canonical, or both — keep consistent with existing behavior; don't expand scope.
- **Scope discipline**: no changes to hidden-command policy, no registration changes in `src/index.ts`, no unrelated completion refactors.
